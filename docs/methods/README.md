## Backtest reports (spec section 13)

`tell backtest <name> [--as-of DATE] [--out DIR] [--refresh]` writes `<name>-<YYYY-MM-DD>.md` and a full copy as `<name>-latest.md` (only when no newer dated report is already in the directory, so a regenerated past date never moves the pointer back; the dated file is the citable source). `tell backtest refresh` (also spelled `tell backtest --refresh`) writes every public report. The weekly workflow runs it with `--out tell-data/site/methods` and commits the reports to [tell-data](https://github.com/karank2512/tell-data/tree/main/site/methods), never here (ADR 0025); the index below lists only reports a maintainer regenerated by hand into this directory. The per-command `--refresh` flag means something narrower: fetch external inputs missing from the cache. Only `velocity-lead --refresh` fetches anything (Wayback CDX listings into `tell-private/cache/wayback`), and the weekly workflow never passes it and has no `tell-private` checkout, so the Wayback reconstruction in 13.2 is fetched only by a maintainer running `tell backtest velocity-lead --refresh` locally; `weekly.yml` reads the cache only and reports unfetched boards as such. Templates: `docs/methods/templates/`. Each report states the question, the cohort, N, the query or script, the numbers, the caveats and the date. A number with N under 30 is printed as "(N=12; too small to quote)" and the report's front matter then says `quotable: false`; launch drafts and resume lines quote only `quotable: true` reports, and a lead-time figure (the days between a Form D and its first press mention, a filing-first share) also needs N of at least 100 and full 60-day follow-up (ADR 0041, [docs/launch/README.md](../launch/README.md)).

### Filling the speed-vs-press cohort (13.1)

The 13.1 cohort is every non-amendment Form D of the last 90 days linked to a monitored
company by a trusted link: rules R1-R4 with no guard failure recorded in
`payload.match.guard_failed`, a reviewer's link (`rule = manual`), or the issuer's CIK when
that CIK was set by such a link. R5 and R6 matches, guard failures and CIK matches vouched for
only by them are excluded (the 2026-10-14 production audit found 20 of 41 Form D auto-links
were the wrong company). Its press is the `news_funding` events from 14 days before to
60 days after each filing. Left to the scheduled jobs, that takes 90 days of daily-index
collection, and the press of any older filing is never queried (scheduled news runs ask
Google News for `when:7d` only). Three commands fill it within days of cutover, in order:

1. `tell backfill formd --quarter YYYYQn [...]` loads the SEC quarterly Form D data sets as
   `edgar` events with `payload.backfill = true` (default `--since-days 120`; `--file` for a
   ZIP already on disk). It needs a real `SEC_USER_AGENT` to download and refuses the
   placeholder. Idempotent. Details: [docs/sources/edgar.md](../sources/edgar.md).
2. `tell resolve` links the filings to companies (R1-R4; CIK matches are linked at load).
3. `tell ingest --source news --cohort formd --when-days 120` queries Google News with
   `when:120d` for every company linked to a Form D of the last 90 days, under the usual
   budgets and redaction. Idempotent. Details: [docs/sources/news.md](../sources/news.md).

Then `tell backtest speed-vs-press`. While N is under 100 the command prints a one-line hint
naming these commands on stderr (the report itself says "sample too small").

`alert_at`: EDGAR publishes a day's form index at about 02:02 UTC the next day, so no
scheduled run sees a filing before filing date + 26 h. `alert_at` is the event's
`observed_at` only when a scheduled run saw the filing promptly: `payload.backfill` is not
set and `observed_at` is within 36 h of the filing date 00:00 UTC (26 h + the 6-hour cadence
+ 4 h for one late run; 54 h at the daily cadence). Filings from the quarterly data sets,
from a catch-up run days later, or with `observed_at` before the filing date are estimated
at filing date + 1 day 02:00 UTC + the cadence (32 h at 6 h). The cadence is a parameter of
`build_report` / `compute` (`cadence_hours`, default 6; 24 when `TELL_RUNS_PER_DAY` is not 4,
see `ingest_cadence_hours`). The report counts observed and estimated values, adds the median
over observed filings only, and labels the alert median "estimated" with a notice when more
than half are estimates, which is the case for a cohort filled by the backfill.

Caveat: the SPEC window (14 days before to 60 days after the filing) misses same-round press
published more than 14 days before the filing; such a round counts as no press, or as filing
first, so the filing-first shares lean high. When the newest posted data set ends
before the 90-day window, date the report at that quarter's end (`--as-of`) and widen the
news windows to match (`--cohort-days`, `--when-days`; see the news page).

### Manual interventions and "weeks unattended"

SPEC 13.4 defines "weeks unattended" as days since the last manual intervention needed to
keep ingest green, from the `runs` table, divided by 7. The `runs` table cannot see a
human, so an intervention is a run that carries the marker `runs.notes.manual = true`,
written by the run lifecycle (`tell/collectors/base.py`) on every run recorded while the
marker is on:

- `TELL_RUN_MANUAL=true` in the environment. `ingest.yml` sets it to
  `${{ github.event_name == 'workflow_dispatch' }}`, so a run dispatched by hand from the
  Actions page or `gh workflow run ingest.yml -f source=...` (the way one collector is
  re-run after a fix) marks every run it records, and a scheduled run never does.
- The global CLI flag `tell --manual <command>` (for example
  `tell --manual ingest --source lever --force` after a hotfix from a terminal), which
  wins over the variable for that invocation.

`tell backtest ops` anchors the unattended period on the latest marked run (its
`finished_at`); with no marked run it counts from the first run ever and the report says
so. `tell runlog --week` prints a proxy beside it, the weeks since the last gap of more
than 24 hours without a successful scheduled run, as a cross-check for fixes nobody marked.
Runs of the nightly intake reader (`source = intake`, which runs in `tell-private`) and of
the one-off Form D backfill (`source = edgar_backfill`) are not pipeline runs: they count
toward neither the success rate nor the anchor. Rule for the
operator and rationale: ADR 0028; deployment side: `docs/deploy/github-actions.md`,
"Re-running one source".

### Freshness p95 (13.4, SPEC section 12)

SPEC section 12 writes freshness as the 95th percentile of `observed_at - occurred_at` over
the last 24 hours of events. Read literally, that is the age of whatever tell reads for the
first time: the first dated `ops` report (2026-10-19) printed 23298.1 h (N=455) because 66
of its 455 events were company-blog posts from 2015 to 2026, read when tell discovered each
blog's feed (company feeds had no first-poll rule; boards did, ADR 0023). ADR 0043 reads the
definition as tell's lag, which is what the SPEC's own target assumes ("four runs a day keeps
p95 freshness under 12 hours for ATS and filings", section 11). `health.json`, the Slack
context line, `tell runlog --week` and `tell backtest ops` share one implementation,
`tell.publish.health.freshness`:

- **Lag**: `observed_at` minus the earliest moment tell could have seen the event. That is
  the source's own timestamp (`occurred_at`; for EDGAR, filing date + 26 h, when the daily
  index lists the filing), moved forward to tell's previous look at the same place when that
  look listed the whole place and did not include the event: the board's previous poll
  (`posting_observations`) or the company's previous Google News query
  (`runs.notes.polled`). Negative lags count as zero.
- **Left out, and counted beside N**: *first looks* (a board's first poll,
  `payload.first_poll`, or any ATS event with no earlier poll of its board; a Google News item
  with no earlier query for its company; a company-feed item dated before tell discovered the
  feed, `company_feeds.created_at`; an EDGAR filing, or any other source's event, visible
  before tell's first run of that source), *first-seen-only* events (`occurred_at =
  observed_at`: `job_updated`, `job_closed`, postings without a `posted_at`, keywords of a
  re-worded posting; tell dated them, so their lag is zero by construction) and *backfills*
  (`payload.backfill`, the quarterly Form D data sets, and Google News items of news runs
  whose `runs.notes.when_days` is above 7, the 13.1 cohort fill).
- The `ops` report prints the p95 with its N, the three exclusion counts and a table with
  each source's own p95. Google News reaches the long tail of companies once a week, so news
  dominates the pooled number; boards and EDGAR are read every run.
- Limits: company feeds keep no poll history, so a feed item dated after discovery counts
  from its own date; the EDGAR offset is the index's usual publication time (the rule 13.1
  uses for `alert_at`), so an index that appears later makes EDGAR lags read high.

Freshness in reports written before ADR 0043 is the literal formula; never quote it.
